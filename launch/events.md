## Abstract en inglés (AGNTCon + MCPCon NA, charla de 25 min)

**Title:** Frozen until called: MCP servers and agent sandboxes that wake from microVM snapshots

**Abstract:**
Agents want two things that pull in opposite directions: lots of tools and sandboxes, and none
of them costing anything while idle. Containers are cheap but share a kernel with code you did
not write; VMs are isolated but slow to boot and hungry for RAM. This talk shows a third option:
freeze a booted Firecracker microVM to disk once, then restore it on
demand.

We will walk through kindling, an Apache-2.0 runtime that does this on Linux (Firecracker) and
macOS (Virtualization.framework). It is used two ways. First, any npm or PyPI MCP server becomes a
service behind one gateway: it sleeps as a file, wakes on the first tool call and goes back to
sleep, with the tool inventory served from the handshake without waking anything. Second, a
multi-tenant sandbox gateway for code agents that speaks the E2B and OpenSandbox APIs, so
existing SDKs and agent frameworks switch backends with an environment variable.

Numbers, with how they were measured: on a nested-virtualization EC2 instance, claiming a
pre-warmed sandbox takes 0.8–1.1 ms and restoring a cold one 76–91 ms, against 0.91–1.11 s for
OpenSandbox 1.2.1 on Kubernetes on the same instance type. Every figure comes with its script and
its caveats, including where the other system wins. We will also cover what broke: orphaned
VMMs, burst concurrency at 50 creates, egress control by SNI, and why a guest has to be treated
as hostile. Attendees leave with a working recipe for running an MCP server or an agent's code
in a microVM on their own laptop.

**Format alternative (lightning, 5 min):** live demo: `kling mcp add` an npm server, freeze it,
call a tool from an agent and watch it thaw, then point an unmodified E2B SDK script at the same
host.

## Abstract en español (T3chFest / Nerdearla / PyConES, 30–40 min)

**Título:** Máquinas congeladas: sandboxes para agentes de IA que despiertan en milisegundos

**Resumen:**
Los agentes de código ejecutan lo que escribe un modelo, y alguien tiene que decidir dónde. En un
contenedor, el código ajeno comparte kernel con tu máquina. En una VM de las de siempre, cada
sandbox tarda segundos en arrancar y ocupa memoria aunque no haga nada. Las plataformas
gestionadas lo resuelven a cambio de mandar tu código y tus datos a la nube de otro.

En esta charla contamos cómo funciona kindling, un runtime libre (Apache-2.0) que arranca una
microVM una sola vez, la congela en disco y la descongela cuando hace falta: Firecracker en
Linux y Virtualization.framework en Mac. Una máquina congelada es un fichero que no gasta CPU ni
RAM. Con eso montamos tres cosas: sandboxes multiinquilino que hablan las APIs de E2B y de
OpenSandbox (los SDK y frameworks que ya usas cambian de backend con una variable de entorno);
servidores MCP que se despiertan con la primera llamada de una herramienta; y una base de datos
desechable por cada test.

Damos números y cómo medirlos tú mismo: en una EC2 con virtualización anidada, reclamar un sandbox
precalentado cuesta entre 0,8 y 1,1 ms y restaurar uno en frío entre 76 y 91 ms, con el script y
la lista de salvedades al lado, incluidas las cosas en las que la otra opción gana. Y contamos lo
que salió mal: procesos huérfanos, ráfagas de 50 creaciones a la vez, controlar la salida a
internet por SNI y por qué hay que tratar al invitado como hostil. La demo va en directo, en un
portátil.

**Público:** gente de backend, plataforma y Python o Go que esté poniendo agentes en producción.
No hace falta saber de virtualización.
